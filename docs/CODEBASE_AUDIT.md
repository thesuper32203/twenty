# Codebase technical audit

Audit date: 2026-10-19. Source revision: `4b4acf88`. Scope: repository source and deployment files only. This audit did not start the application, connect to a production database, run the test suite, probe endpoints, or assess deployed secrets and network controls. **Implemented** below means an executable source path is present, not that a production deployment was proven healthy. **Partial** means a path exists with an identifiable limitation. **Unverified** means source inspection cannot establish runtime behavior. **Missing** means no implementation was found in the inspected source.

## Executive summary

Twenty is a Yarn 4/Nx monorepo. The principal runtime is a React/Vite frontend and a NestJS server, with a separate BullMQ worker. PostgreSQL holds core entities and per-workspace CRM data; Redis supports queues, sessions, cache, and locks. The server exposes core, metadata, and admin GraphQL APIs, metadata-generated workspace CRUD, REST CRUD, and MCP. AI agents, workflows, messaging, calendars, email campaigns, applications, and observability are substantive implementations, but they require deployment configuration and runtime verification. The requested Prisma audit maps instead to **TypeORM core entities plus TwentyORM workspace records**; there is no Prisma schema in this checkout.

The most important production decisions are to harden the supplied Compose configuration, prove tenant isolation across every API and worker path, rehearse upgrades and backup restoration, and validate queue and AI recovery under process loss. The source contains safeguards, but a repository inspection cannot certify those system properties.

## 3. Database and migrations

**No Prisma schema, client, or Prisma migrations were found.** [`core.datasource.ts`](../packages/twenty-server/src/database/typeorm/core/core.datasource.ts) configures TypeORM against PostgreSQL `core`, disables `synchronize` and automatic migrations, and loads historical migrations only for legacy tracking. Core TypeORM entities include [`workspace.entity.ts`](../packages/twenty-server/src/engine/core-modules/workspace/workspace.entity.ts), [`object-metadata.entity.ts`](../packages/twenty-server/src/engine/metadata-modules/object-metadata/object-metadata.entity.ts), [`field-metadata.entity.ts`](../packages/twenty-server/src/engine/metadata-modules/field-metadata/field-metadata.entity.ts), [`role.entity.ts`](../packages/twenty-server/src/engine/metadata-modules/role/role.entity.ts), and [`agent.entity.ts`](../packages/twenty-server/src/engine/metadata-modules/ai/ai-agent/entities/agent.entity.ts). The metadata entities declare workspace-scoped unique indexes and TypeORM relations; `FieldMetadataEntity` has a relation-type check constraint.

Workspace CRM records use [`workspace-data-source.service.ts`](../packages/twenty-server/src/engine/twenty-orm/datasource/workspace-data-source.service.ts), [`workspace-data-source.ts`](../packages/twenty-server/src/engine/twenty-orm/datasource/workspace-data-source.ts), [`workspace-repository.ts`](../packages/twenty-server/src/engine/twenty-orm/repository/workspace-repository.ts), and workspace auth/metadata context. The service creates PostgreSQL pools for primary and optional replica. Standard typed entities such as [`person.workspace-entity.ts`](../packages/twenty-server/src/modules/person/standard-objects/person.workspace-entity.ts), [`company.workspace-entity.ts`](../packages/twenty-server/src/modules/company/standard-objects/company.workspace-entity.ts), and [`opportunity.workspace-entity.ts`](../packages/twenty-server/src/modules/opportunity/standard-objects/opportunity.workspace-entity.ts) describe fields and relations. [`create-standard-flat-object-metadata.util.ts`](../packages/twenty-server/src/engine/workspace-manager/twenty-standard-application/utils/object-metadata/create-standard-flat-object-metadata.util.ts) supplies standard object metadata. These class definitions alone are not proof of deployed SQL constraints; verify generated schema and indexes in a migrated database.

New core schema/data changes use registered fast/slow instance commands and per-workspace commands, documented in [`UPGRADE_COMMANDS.md`](../packages/twenty-server/docs/UPGRADE_COMMANDS.md) and driven by [`run-instance-commands.command.ts`](../packages/twenty-server/src/database/commands/run-instance-commands.command.ts). Runtime metadata changes use [`workspace-migration-runner.service.ts`](../packages/twenty-server/src/engine/workspace-manager/workspace-migration/workspace-migration-runner/services/workspace-migration-runner.service.ts), which opens a TypeORM query-runner transaction, sets lock timeout, commits/rolls back, then invalidates caches. Deferred migration actions have a recovery service and queue job in the same directory. **Unverified:** real upgrade state, pending slow commands, rollback compatibility, replica lag, backup/restore, and table/index health.

## 5. Background processing

[`queue-worker.ts`](../packages/twenty-server/src/queue-worker/queue-worker.ts) starts a separate Nest application context; [`queue-worker.module.ts`](../packages/twenty-server/src/queue-worker/queue-worker.module.ts) imports jobs and drains workers on shutdown. [`message-queue.service.ts`](../packages/twenty-server/src/engine/core-modules/message-queue/services/message-queue.service.ts) abstracts add/bulk/cron/work. [`message-queue.explorer.ts`](../packages/twenty-server/src/engine/core-modules/message-queue/message-queue.explorer.ts) discovers decorated processors and honors enabled/excluded queue configuration. [`message-queue-core.module.ts`](../packages/twenty-server/src/engine/core-modules/message-queue/message-queue-core.module.ts) selects BullMQ or synchronous driver.

The production BullMQ path in [`bullmq.driver.ts`](../packages/twenty-server/src/engine/core-modules/message-queue/drivers/bullmq.driver.ts) stores jobs/schedulers in Redis, sets attempts and optional backoff/delay/deduplication, exposes queue gauges, and supports global concurrency. [`message-queue-worker-config.constant.ts`](../packages/twenty-server/src/engine/core-modules/message-queue/message-queue-worker-config.constant.ts) sets explicit per-queue concurrency, lock duration, stalled-count and shutdown policy. [`queue-retention.constants.ts`](../packages/twenty-server/src/engine/core-modules/message-queue/constants/queue-retention.constants.ts) removes completed jobs after four hours or 1,000 entries and failed jobs after seven days or 1,000 entries. Thus failed-job history is **not** a permanent audit trail. Retry is opt-in per enqueue (`retryLimit` defaults to zero in the driver), so it must be checked for each critical job.

Scheduling uses BullMQ job schedulers and cron dispatch/Redis lock deduplication via [`cron-trigger-deduplication.service.ts`](../packages/twenty-server/src/engine/core-modules/cron/services/cron-trigger-deduplication.service.ts). Recovery is feature-specific: [`workflow-handle-staled-runs.workspace-service.ts`](../packages/twenty-server/src/modules/workflow/workflow-runner/workflow-run-queue/workspace-services/workflow-handle-staled-runs.workspace-service.ts) resets stale queued runs and monitors stuck running runs; [`pending-wake-up-sweep.cron.job.ts`](../packages/twenty-server/src/engine/core-modules/pending-wake-up/crons/jobs/pending-wake-up-sweep.cron.job.ts) sweeps persisted wake-ups; deferred workspace migrations have a recovery service. BullMQ persistence supports restart recovery **if Redis data survives**. Exactly-once execution is **not established**; handlers and external side effects require idempotency review.

This is evidence of controls, **not** a vulnerability-free finding. The `secure` cookie flag depends on a correct HTTPS `SERVER_URL` and proxy configuration.

## 8. Verification and next steps

Repository counts from file inventory: approximately 1,637 server `*.spec.ts` files, 1,533 frontend `*.test.ts(x)`/`*.spec.ts(x)` files, and nine E2E `*.spec.ts`/`*.test.ts` files under `twenty-e2e-testing`; these are file counts, not coverage or pass results. Relevant CI definitions include `.github/workflows/ci-front.yaml`, `.github/workflows/ci-e2e-main.yaml`, and server workflows. No tests were run for this read-only audit, so **working** claims above are source-backed implementation claims only.

Before production modification, establish a baseline in a disposable environment: install with the pinned Yarn/Node versions; run targeted server/frontend and E2E suites; provision PostgreSQL and durable Redis; apply fast **and slow** upgrade commands; compare actual schema/indexes to metadata; test cross-tenant access; exercise workflow/agent/job restarts; confirm email/OAuth/webhook credentials; load-test high-cardinality record queries and concurrent workers; then validate backup restoration and alerts. Record the exact deployment revision, configuration, migration cursor, test results and remaining exceptions. Avoid treating example Compose defaults as production configuration.
